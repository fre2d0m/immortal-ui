# 泛物联网视觉组件研究与现有目录评估

研究日期：2026-11-04。对象：Immortal UI 当前工作区。本文是设计研究和候选定义，不是新增组件的交付清单。

**结论：现有 17 个组件可以作为第一层基础，但不足以构成专业物联网组件库。** 当前目录主要按表现形式拆分，设备能力、控制权、测量质量和业务过程还没有形成完整结构。下一轮应保留 Graphite 的材质体系，建立“共用基础、设备能力、业务组合”三个层次，再以真实任务检验设计。

本次纳入 35 项官方资料，涉及 Apple Home、Home Assistant、Philips Hue、Google Home、Siemens iX、Rockwell PlantPAx、Ignition、ThingsBoard、Priva、Netafim、Metasys、EcoStruxure、Grafana、Vaisala、The Things Network、AWS IoT、OPC UA、ifm 和 Sentek 共 19 套产品或技术体系。实际查看了 5 张官方网页示例图及 Netafim 手册的 2 页界面图。没有登录这些产品的真实设备环境。

证据标记：**V** = 已查看官方图像及相关说明；**D** = 已读取官方文字资料；**I** = 仅取得官方页面的检索摘录，正文访问受限。视觉判断只使用 V；I 只作为补充线索。官方示例图可能沿用旧版素材：Priva 图内日期为 2022 年，Ignition 示例图为 2020 年，不能当作最新版本的完整外观。

**本项目的视觉方向（设计判断）：** 用清楚的能力控件承接消费级体验，用真实状态、关联趋势和可解释的操作约束承接专业性。专业感应来自信息准确和任务完整，而非增加黑底、仪表盘、数字密度或装饰线。

现有 Graphite 的基础材质可以保留。重点调整信息层级和组件形态：在设备概览里展示当前状态与一个主要操作；展开后再显示调节、反馈和诊断。面板负责聚合，凹槽负责承载局部内容，按钮负责动作，标签负责状态，不能每一种信息都做成凸起按钮。

## 3. 现有 17 个组件的逐项评估

依据当前源文件及目录定义，不把演示页面等同于设备能力实现。

| 当前组件 | 已有基础 | 需要改变或补齐 |
| --- | --- | --- |
| Sensor reading | 数值、单位、精度、缺失、离线与小趋势 | 增加测量质量、采样时间、量程/目标上下文；提供紧凑行与详细面板两种组合方式 |
| Device card | 设备身份、位置、电量与信号 | 移入“设备与空间”；通过 capability 组合展示，不把每台设备固定成同一张卡 |
| Device status | 在线、预警、离线、初始化 | 拆开连接、运行、告警、检修等维度；当前 warning 与连接状态混在同一枚举里 |
| Signal strength | RSSI 和缺失显示 | 现在 -55/-67/-80 dBm 的固定分段仅为显示启发式；需要协议/指标信息及可配置分级，LoRaWAN 还应考虑 SNR 等上下文 |
| Data freshness | 最新、过期、离线快照、未知 | 时效是一个维度，不能替代质量；采样年龄、接收时间、预计上报间隔需分别明确 |
| Telemetry chart | 零值与断点保留，可查看数据表 | 发展为多序列趋势、目标线/区间、事件标注、实时/历史切换；明确时区、聚合粒度和时间窗口 |
| Range gauge | 量程、目标范围、越界与无值 | 保留适用场景；批量读数优先比较直线量程。液位、设定值、压力不应只因都为数字而共用半环 |
| Interval histogram | 非负时段值、零与缺失、表格回读 | 当前其实是时段柱图，不是统计频数直方图；命名和用途要分开。平均照度与累计光量、瞬时流量与累计水量也需分开 |
| Control mode | 模式切换和只读态 | 手动/自动是运行策略，AI 是建议或决策来源；另有本地/远程、控制者、覆盖期限。需要重建模型 |
| Actuator switch | 请求与回读分离、异步错误反馈 | 作为二值能力模块保留；补状态未知、受控/锁定原因。泵、锁、阀等需专门组合 |
| Setpoint control | 草稿、范围、步进、显式应用与回执 | 增加当前生效设定、测量值与控制输出的区分；编辑期间外部值变化需要冲突提示。当前 value 更新会直接重置草稿 |
| Threshold control | 上下界编辑与范围校验 | 应区分目标运行区间和告警规则；规则另有迟滞、持续时间、恢复条件、启用窗口 |
| Directional control | 开/停/关、位置值、先停再换向 | 补目标位置、实际反馈、端限位、卡滞、标定与联锁原因；当前未知方向不可开始操作，需说明状态来源及恢复方式 |
| Command status | 请求值、回读值、等待、确认、失败 | 四态不足以表达长过程。Promise 完成的含义依赖接入方，不能普遍代表物理动作完成；超时还需要表达结果未知 |
| Alert card | 确认异步反馈，文字明确“确认不代表恢复” | 数据结构仍缺 active/cleared、确认人、恢复时间、搁置等事实；需发展为完整告警状态行与详情 |
| Event timeline | 事件按时间阅读 | 补操作者、变化前后值、来源、关联命令/告警；需要筛选和详情，而非仅一组通知 |
| Automation note | 建议与执行分离 | 升级为建议依据、受影响设备、预期变更、有效期和执行结果；保留“接受建议不等于已经执行”的边界 |

## 4. 组件建模需要同时保留的维度

OPC UA 为值提供质量与源/服务端时间戳，AWS Shadow 区分期望与上报状态；Metasys 明确当前控制优先级。这些资料共同说明：一个 online 或 success 标签无法回答所有问题。[S15]、[S16]、[S20]

以下是本项目建议的统一设计约定，具体字段和可操作性须由接入系统提供：

| 问题 | 应独立表达的事实 | 界面例子 |
| --- | --- | --- |
| 这是谁的数据？ | 资产、位置、测点、物理量、单位 | “北侧温室 / 冠层温度 / 1 号探头” |
| 数据是否可用？ | 质量、采样时间、接收时间、缺失原因 | “24.6 °C · 12 秒前采样 · 质量正常” |
| 设备正在做什么？ | 实际状态、反馈位置/速度、端限位 | “开启中 · 实际开度 35%” |
| 谁决定当前动作？ | 本地/远程、控制来源、运行策略、覆盖期限 | “本地手动接管 · 远程只读” |
| 为什么操作不了？ | 权限、连接、联锁、许可条件、任务占用 | “雨保护生效，暂停开窗” |
| 我的操作到哪一步了？ | 请求、接收、执行、反馈验证、失败或未知 | “已接收，等待位置反馈” |
| 异常处理到哪一步了？ | 条件是否仍存在、是否确认、是否搁置、处理记录 | “异常仍存在 · 已确认” |

这些维度不应常驻堆满卡片。默认面板显示决定当前任务的部分；异常时展开原因；诊断细节按需查看。采样、连通与运行状态必须允许互相不同，例如连接在线但某测点故障，或设备离线但历史读数仍可查看。

### 测量类型如何影响界面

“复用读数基础”不意味着“所有传感器长成同一张卡”。以下是从领域资料推导的组件变体；阈值、公式、频带和计算口径由具体业务提供，界面不内置通用的“健康范围”。

| 测量族 | 所需的专业上下文 | 建议的视觉结构与边界 |
| --- | --- | --- |
| 温度、湿度与露点 | 测点位置、直接测量或计算、计算依赖及可用性。Vaisala 特定探头在加热条件下可能需要外部温度才能提供某些参数 [S34] | 关联测量组；依赖不可用时具体参数标记不可用，不将整台探头简单视为正常或离线 |
| 土壤水分与盐分 | 深度、探头、分层与汇总范围；Sentek 将不同深度与管理线放在同一分析语境 [S32] | 按深度排列的小趋势/剖面，根区汇总单独说明；不把空气湿度和土壤含水量混为同一种百分数 |
| 流量、压力与累计量 | 瞬时测量、周期累计、主管线/测点关系 | 流量趋势配累计读数，压力独立标尺；累计量需要时间窗与复位记录，不能把流量曲线直接称为用水量 |
| EC、pH 与配方反馈 | 目标、实际测点、采样时间、运行阶段 | 同一配方下并列对照，分别保留单位和刻度；无实测反馈时显示无数据 |
| 风与降水 | 平均/最大风速、风向、累计周期；Vaisala 的观测定义区分雨强与累计降水 [S35] | 方位刻度加文字，速度统计分列；雨强与累计量分图或明确分轴，风向跨 0° 不按普通线性差值表达 |
| 振动与机械状态 | 转速、采样工况、指标类型、原始信号和频率范围 [S31] | 长期指标趋势、短时波形、频谱分别设计；一个 RMS 数值不能替代全部诊断，模式识别只展示已有分析结果 |
| 电能与电能质量 | 功率/能量、相别、事件、谐波和瞬态记录。Schneider 官方资料将波形关联到电能质量事件 [S33] | 供需概况与专业诊断分层；相位波形、谐波柱图、事件详情各有独立视图 |
| 接点、占用、门磁与漏水 | 物理状态、是否可靠、是否需要处置 | 使用状态图形和变化时间；无数据、无事件、已解除是不同含义，不能统一显示绿色 |

专业传感器的差异应同时进入示例数据和组件说明。传感器类型、物理量、采样方式、安装位置、统计口径分别记录，避免用设备图标代替测量语义。

## 5. 候选模式清单：56 项

这是经过归类的候选库，包含基本展示、设备能力和可复用业务组合，**不代表马上发布 56 个包**。下面的状态及验收要求是本项目的设计提案，不声称每个参考产品都具备全部能力。

优先级：A = 首批深入设计的 12 个样例；B = 基础体系稳定后扩展；C = 明确业务需求后实现。同一编号可复用其他编号，不重复实现基础能力。

### 感知与测量

参照：数值质量与时效 [S12]、[S16]，协议链路 [S29]，校准与记录 [S27]。

| 编号 | 模式与视觉形态 | 必须能表达的内容 | 与现有关系 / 优先级 |
| --- | --- | --- | --- |
| 01 | 测量读数：紧凑行 / 详细读数面板 | 数值、单位、精度、物理量与测点；零、负值、越量程、无效值 | 扩展 Sensor reading / A |
| 02 | 离散传感状态：状态图形加文字 | 门磁、有人、漏水、烟感等事实；未触发、触发、未知、故障，不能把未知当安全 | 新增 / B |

## 6. 首批设计的 12 个评审样例

首批选择 01、06、10、19、20、22、25、26、27、28、30、45。顺序是先建立事实和状态语言，再验证设备差异，最后组合成任务界面。它们不一定各自对应一个发布包。

| 评审样例 | 需要回答的问题 | 可验收的反例 |
| --- | --- | --- |
| 01 测量读数 | 数值是什么、来自哪里、现在能否使用？ | 零值正常显示；负值不被裁掉；无效读数不显示为 0 |
| 06 测量可信度 | 质量和时效是否可分别识别？ | 在线但测点故障；离线但有历史快照；接收时间很新但采样很旧 |
| 10 趋势检查器 | 当前、目标、异常和操作是否能放在同一时间上下文？ | 断点不补线；单位不同不误共轴；历史回看不被自动刷新夺走 |
| 19 灯光控制 | 消费级操作是否一眼可懂？ | 不支持色彩的灯不显示色盘；群组部分失败可追踪；拖动与应用策略明确 |
| 20 温控器 | “目标温度”和“正在制热”能否区分？ | 达到目标后待机；当前模式不支持某项调节；上下目标范围冲突 |
| 22 行程控制 | 用户能否区分命令、运动和到位？ | 无反馈时不显示虚假开度；换向受限有原因；卡滞不只显示 loading |
| 25 设定编辑 | 外部值变化时用户草稿是否可信？ | 另一终端更改设定后提示冲突；应用失败保留草稿和旧的事实值 |
| 26 控制权 | 谁在控制、何时结束、如何归还？ | 本地接管、临时覆盖到期、只读权限；AI 建议不自动冒充控制权 |
| 27 许可与联锁 | 不可操作的原因是否可解释？ | 条件未知与条件不满足分别展示；输入陈旧不能自动判定允许 |
| 28 命令过程 | 接收与完成是否各有证据？ | 网络超时后结果未知；较早回执不覆盖较新操作；设备反馈迟到 |
| 30 告警状态行 | 确认与恢复能否独立辨认？ | 已确认仍异常；已恢复未确认；操作失败不乐观标记为已确认 |
| 45 灌溉运行 | 是否能读懂实际任务进展？ | 程序运行但没有流量；暂停后不继续累计虚假的完成量；总量未知时不造百分比 |

复杂判断由接入系统提供可核验的状态，组件负责表达和交互。UI 验收应使用明确的模拟状态；真实设备验收另行记录，不能用动画完成代替现场执行。

## 7. Components、Blocks 与 Icons 的组织建议

**建议保留四个现有主要入口，但调整边界，并增加设备与运维。** 当前“传感器”下的身份和连接条目并非全是传感器组件；控制类应当有更细的能力索引。

| Components 一级分组 | 二级内容 | 调整目的 |
| --- | --- | --- |
| 感知与测量 | 连续测量、离散状态、多通道、质量/时效、计量/校准 | 按数据及测量语义区分 |
| 数据可视化 | 时间趋势、状态时段、比较/分布、资源流、空间/关系 | 按用户要回答的问题区分 |
| 控制与执行 | 二值、设定、位置/行程、灯光、温控、风机、阀/泵、控制权/联锁、执行过程 | 能力型组件有明确入口 |
| 事件与告警 | 状态行、列表、详情、搁置、规则、操作记录、建议解释 | 从提醒发展到可处理的过程 |
| 设备与空间 | 身份、资产树、区域、链路、工艺关系 | 收纳跨传感和控制的设备基础 |
| 配置与运维 | 接入、配置比较、任务、维护、版本与诊断 | 避免把生命周期能力塞进通用 Device card |

行业作为第二维筛选，例如农业、楼宇、工业、水务、冷链、能源、家居。一个组件只有一个主要归属，但可以关联多个能力与行业标签。侧栏只列真实可用条目；规划条目有独立标记，不能提供不存在的安装命令。

**Blocks 按任务组织，而不只按行业命名。**

| 场景 | 操作任务与主要组合 | 最重要的异常 |
| --- | --- | --- |
| 温室通风与气候调节 | 分区概况、实测/目标趋势、行程控制、控制权、联锁、操作记录 | 雨保护、本地接管、位置反馈缺失 |
| 灌溉及水肥运行 | 当前任务、流量/压力、阀组队列、配方、累计量、暂停/停止反馈 | 无流量、任务等待、测量缺失、部分设备失败 |
| 泵站或储罐输送 | 液位、泵/阀面板、工艺关系、许可条件、运行时段 | 液位未知、联锁阻止、反馈与命令不一致 |
| 楼宇区域舒适度 | 空间列表、温控器、占用状态、日程与临时覆盖 | 日程被覆盖、模式冲突、局部设备不可达 |
| 冷链异常处置 | 超限时段、传感器可信度、校准记录、告警详情、处理记录 | 当前正常但历史异常未处理、期间缺测 |
| 能源供需分析 | 资源流、功率与能量趋势、设备比较、计量边界 | 未计量差额、缺测、统计周期不一致 |
| 设备接入与升级 | 调试步骤、首条有效数据、配置比较、分批任务结果 | 已连接但无有效数据、部分升级失败 |
| 房间灯光与场景 | 设备能力入口、灯光、场景预览、群组反馈 | 部分灯不可达、场景仅部分生效 |

**Icons 需要两个层次。** 第一层是用于导航、标签和按钮的语义图标；第二层是用于工艺图的设备符号，包含连接点、朝向和状态叠加。ThingsBoard 的符号绑定以及 Metasys 的图形分类提供了这种区分的依据。[S14]、[S21]

现有 Icons 六类占位可以保留。后续优先补温度/湿度/压力/流量/液位/EC/pH/光照、风机/泵/阀/卷帘、网关/有线/无线、空间/管路/储罐、资源、状态六组的语义。设备本体、物理量、运行状态不共用同一个含糊图形。颜色及故障标记作为状态层，不为每个状态重画一套毫不相关的图标。

## 8. 三个具体设计演练

以下数值只用于界面演练，不是农业或工业运行建议。

**通风窗：** 顶部显示分区和通风窗名称；实测温度与目标并列；位置区域分别显示实际 35% 与请求 60%。若本地接管或雨保护生效，操作区直接给出原因。开停关保持稳定位置。详细区再显示反馈时间、端限位和最近操作。图形的运动只跟随设备反馈，不跟随点击立即假转动。

**灌溉：** 主信息是当前任务和分区，显示计划 12 m³、累计 8.2 m³、实测流量及阶段。等待下一阀组的原因放在队列中。暂停、停止、跳过属于不同动作，应显示各自结果；若设备未确认，任务状态仍保留已知事实并标记等待。只有具备可信计划总量时才显示完成比例。

**冷链：** 当前温度恢复到目标区间后，历史超限时段仍保留。告警可以同时显示“已恢复、待确认”。详情关联测量断点、校准和操作记录。Vaisala 官方已记录过界面趋势缺口与报告连线不一致的问题，因此图表和导出对缺测的含义必须一致，不能把参照产品当作无需检验的正确答案。[S28]

## 9. 视觉与验收约定

以下是项目规范，不是对所有参考产品的描述。

- active、selected、checked、hover 保持相同字重与几何尺寸。选择由底色、材质、焦点及必要状态标记表达。数值采用等宽数字；有进度/等待文案的操作预留稳定宽度。
- 保留既定面板、按钮和 Tabs 质感。凹陷子容器无额外 1px 边框，shadow-well 使用用户指定的两层内阴影，第二层为 0.5px。
- 主标题直接进入内容，不添加宽字距眉题或装饰箭头。标题、数值、单位、状态、动作有固定阅读顺序。
- 正常态控制色彩数量，警告/故障使用明确语义色加文字。灯光色彩、图表序列色与告警色应有清楚的使用范围。
- 让只读数值看起来可读，让按钮看起来可操作；纯状态标签不带按钮凸起阴影。不要用灰掉一整张面板来掩盖局部不可操作原因。
- 同一组件支持概览与细节组合，列表、密集监控和移动端有不同密度。信息缩减仍保留状态来源和关键动作。
- 图表要可读到精确值，图例、触屏和键盘路径都能访问；不把 hover tooltip 作为唯一信息入口。
- 普通页面不出现粗原生滚动条；表格确有二维数据时保留可发现的滚动能力，不能为截图隐藏数据。分清“视觉处理”与“禁止滚动”。
- 每个组件必须展示正常、未知、陈旧/离线、失败、只读/禁用，以及与自身能力相关的过程状态。没有实际状态的设计图不能算组件完成。
- 先验收 320px、常用桌面宽度及多设备密度，再组合 Blocks。长中文设备名、长单位/状态、负数、极值、空数据和部分成功都应进入样例。

## 10. 本轮已实施与仍待设计

**已实施：** 去掉导航、筛选和分段选择公共选中态中的加粗覆盖；将状态切换保持字重和占位不变写入基础规范。网站、主题源和生成镜像已同步。

**待设计：** 56 项候选、12 个首批样例、新分组结构及上述 Blocks 均为研究建议，本轮没有批量新增组件，也没有提交或发布。现有 17 个组件和演示 Blocks 仍是当前实现范围。
